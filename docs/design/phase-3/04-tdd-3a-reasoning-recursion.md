## 1. Existing capability vs. what's actually being added

**Existing (verified by direct code read, not assumed):**
- `resolve_mode_and_level` (`domain/modes/__init__.py:53-84`) already
  dispatches `reasoning_level_hint=4` (or any hint ≥4), with no explicit
  `reasoning_mode_hint`, to `ReasoningMode.MULTI_STEP` — the final
  fallthrough line, `return ReasoningMode.MULTI_STEP, level`.
- `modes/multi_step.py`'s `CONFIG` is a real, fully wired `ModeConfig`
  (`mode=MULTI_STEP, minimum_hypotheses=3, max_step_depth=3`) — not
  gated by `NotImplementedModeError` (that treatment applies only to
  `ReasoningMode.COLLABORATIVE`, `domain/modes/__init__.py:45-49`).
- `pipeline.run()` executes Multi-step today as a **single, non-recursive
  pass** through the identical 14-step body every other non-Reactive mode
  uses — no different from Analytical or Strategic in actual behavior,
  despite the different `ModeConfig`.
- `ReasoningProcess.parent_process_id` and `ReasoningRequest.parent_process_id`
  already exist and are already threaded through
  (`pipeline.py:180`, ORM mapping, API/event payload wiring) — but always
  as a **caller-supplied passthrough**, never self-generated by a
  recursive sub-call. (This field is shared with the Phase 2D-D
  correction-signal extension's own use of process lineage — see §7.)

**What's being added:** the actual recursion — a mechanism that, for a
Multi-step decision that depends on an unresolved sub-question, invokes
the pipeline again for that sub-question (up to `max_step_depth`),
threads `parent_process_id` to link the chain, and aggregates the
top-level decision's confidence as the **chain minimum** (per
`multi_step.py`'s own docstring, not an average).

## 2. Open architectural forks — genuinely undocumented, not silently resolved

No Bible part, architecture doc, ADR, or design doc specifies the
recursion mechanism's shape beyond the one docstring sentence quoted
above. Both forks below are real judgment calls this TDD surfaces rather
than invents past.

### Fork 3A-1 — Internal self-recursion vs. caller-orchestrated chaining

**Evidence.** `multi_step.py`'s docstring describes *"a decision built
from a chain of dependent sub-decisions, each individually traced"* and
*"aggregate is the minimum across the chain, never an average... full
chain explainable step by step"* — phrasing that describes a single
logical operation producing one final `Decision`, not a caller manually
stitching together independent top-level calls. Bible Part 9's
boundary language (*"Reasoning belongs to the Reasoning Engine"*,
`part-09-planning-engine.md:611`) argues recursion mechanics belong
inside `reasoning-engine`, not duplicated in every caller.

- **Option A (recommended).** `pipeline.run()` detects the trigger
  condition itself (Fork 3A-2) and recursively invokes an internal helper
  for the derived sub-question, aggregating before returning **one**
  `Decision`/`ReasoningTrace` to the original caller — the caller sees a
  single RPC round trip regardless of how many internal steps the chain
  took.
- **Option B.** No internal recursion at all; `reasoning-engine` only
  continues honoring `parent_process_id` as a caller-supplied passthrough
  (already true today); any "chain" is entirely the calling engine's own
  responsibility (issuing multiple separate `reasoning.request`s and
  aggregating itself).

**Recommendation: Option A**, since it keeps chain-aggregation logic
(confidence-as-minimum, step-by-step explainability) in the one place
that already owns confidence scoring and explanation generation, and
matches the docstring's framing of Multi-step as one mode producing one
decision. **Requires explicit approval — this is not extracted from any
authoritative document.**

### Fork 3A-2 — Sub-question detection heuristic

**Evidence.** No document specifies how the pipeline should recognize
"this decision depends on an unresolved sub-question." The pipeline
already computes, before finalizing a decision: `confidence.composite`
(vs. `verify_threshold`/`override_threshold`), `below_minimum`
(insufficient alternatives survived — `alternative_generation`'s own
signal), and constraint violations.

- **Option A (recommended, minimal-new-surface).** Trigger recursion
  when `mode is MULTI_STEP`, `confidence.composite < verify_threshold`
  (the same threshold already gating "decided" vs. "awaiting_human_override"
  for every other mode), and `depth < config.max_step_depth`. Derive the
  sub-question's `objective_text` from the chosen alternative's weakest
  supporting-evidence gap (a structural signal `decision_matrix.py`
  already computes per alternative — no new model capability required).
  Recurse once, fold the sub-decision's result into the parent's context/
  evidence, re-run scoring for the parent at `depth+1`.
- **Option B.** Require an explicit, model-emitted "this needs resolving
  first" signal — needs a new structured field on the hypothesis-
  generation request/response contract (a real, disclosed
  `ai-model-orchestration-engine`-facing schema change, and a dependency
  on prompt-engineering work not otherwise in this TDD's scope).

**Recommendation: Option A** — reuses signals the pipeline already
computes, adds no new upstream contract, and keeps the mechanism testable
via structural assertions (doc 16 §5) without depending on any specific
model's behavior. **Requires explicit approval.**

### Trigger-condition safety bound (not a fork — a hard requirement)

At `depth == max_step_depth` with the sub-question still unresolved: the
pipeline **must not** raise or hang. Per the existing `_fail()` precedent
(*"failure should improve future reasoning rather than terminate
execution"*, `pipeline.py:449-452`) and the existing degraded-outcome
pattern (`context_degraded` → `outcome="degraded"`), the correct behavior
is to return the best-available chain result with `outcome="degraded"`
and confidence penalized accordingly — never an unbounded loop, never an
unhandled exception. This mirrors an existing pattern, not a new one.

## 3. Design (pending Fork 3A-1/3A-2 approval)

Assuming Option A for both forks:

1. `pipeline.py` gains a new mode-specific branch,
   `if mode is ReasoningMode.MULTI_STEP:`, structurally parallel to the
   existing `REACTIVE` branch but not an early return — it wraps the
   existing common-body logic with a depth-aware recursion check inserted
   after confidence is first computed (`pipeline.py:364-371`'s existing
   `confidence_module.estimate_confidence(...)` call site).
2. A new internal helper, `_maybe_recurse(...)`, encapsulates the Fork
   3A-2 trigger check and the recursive `run()` invocation (passed
   `depth=depth+1`, `parent_process_id=process.id`, a derived
   `objective_text`). `run()`'s public signature is unchanged — `depth`
   is an internal parameter, defaulted to `0`, never caller-exposed
   (`ReasoningRequest` gains no new field for this).
3. On a successful sub-resolution: the parent's `confidence.composite` is
   recomputed as `min(parent_confidence, child_confidence)`; the parent's
   `ReasoningTrace` gains a `child_process_ids: list[UUID] = []` field
   (additive, defaulted, per ADR-024) so the full chain is traceable
   without changing `ReasoningTrace`'s existing shape for every
   non-recursive call.
4. `ReasoningRepository` gains one new method,
   `list_child_processes(parent_process_id: UUID) -> list[ReasoningProcess]`,
   for reconstructing a chain's full lineage — needed by observability
   and by any future caller wanting the full explainable chain (doc 16
   §5's "full chain explainable step by step" requirement).

## 4. Required contract additions

One additive, optional field on an existing, already-published payload —
no new event subject:

- `nova_contracts.events.reasoning.ReasoningProcessCompletedPayload`
  gains `parent_process_id: UUID | None = None` (currently absent from
  the payload despite `ReasoningProcess` itself already carrying the
  field). This lets downstream consumers (memory-engine's Decision
  Memory, future observability) see chain structure without a new RPC.
  ADR-024-compliant: optional, defaulted, breaks nothing for any existing
  consumer.

No new `nova-contracts` payload, no new event subject, no new REST
endpoint. `pipeline.py`'s public `run()` signature is unchanged.

## 5. Failure and degraded behavior

| Condition | Behavior |
|---|---|
| Sub-question resolves within `max_step_depth` | Parent decision finalizes with chain-minimum confidence; `outcome` follows the existing threshold logic (`decided`/`degraded`/`awaiting_human_override`), unchanged. |
| `max_step_depth` reached, still unresolved | Parent decision finalizes using the best available (unresolved) alternative; `outcome="degraded"`, confidence penalized — never an exception, never an unbounded loop (§2, safety bound). |
| Recursive sub-call itself fails (`hypothesis_generation.HypothesisGenerationError`, no eligible alternatives, etc.) | Treated identically to `max_step_depth` reached — the parent does not propagate the child's failure as its own failure; it degrades gracefully, consistent with `_fail()`'s existing "every failure still produces a Decision" discipline. |
| `context_degraded` at any recursion level | Existing behavior unchanged — degrades that level's contribution; does not by itself trigger recursion (recursion is about unresolved sub-questions, not degraded context, which already has its own handling). |

## 6. Observability requirements

New metrics, following the codebase's existing `snake_case`/`_total`/
histogram conventions (no new metrics backend — reuses
`nova-observability`, already a dependency of `reasoning-engine`):

- `reasoning_multistep_recursion_triggered_total` (counter) — incremented
  each time Fork 3A-2's trigger condition fires.
- `reasoning_multistep_recursion_depth` (histogram) — the final depth
  reached per completed Multi-step process (0 = never recursed).
- `reasoning_multistep_recursion_exhausted_total` (counter) — incremented
  when `max_step_depth` is reached without resolution (the degraded-exit
  path in §5).

Existing `correlation_id`-based tracing (already required for every
response, per the Phase 2D-A acceptance criterion) extends naturally to
a recursive chain since every child process still carries the same
`correlation_id` as its parent — no new tracing mechanism needed.

## 7. Security boundaries

None new. Recursion happens entirely within `reasoning-engine`'s own
process boundary, over data already retrieved for the parent request —
no new upstream port, no new privilege, no new data access. ADR-032 does
not apply (no privileged-capability gating occurs in `reasoning-engine`).
The shared use of `parent_process_id` with Phase 2D-D's correction-signal
extension is a naming/field-reuse question, not a security one — both
uses mean "this process is logically subordinate to that other process";
TDD implementation must confirm (unit test) that a correction-linked
`parent_process_id` and a recursion-linked one never collide in a way
that misattributes a chain (e.g., `list_child_processes` must not
conflate a correction-follow-up with a recursion sub-step — they are
distinguishable via `ReasoningProcess.reasoning_mode`/an explicit
discriminator to be finalized during implementation, not invented here).

## 8. Testing strategy

**Unit (fake-backed, default suite):**
- `resolve_mode_and_level` branch coverage (already exists — Phase 2B's
  `test_modes.py` — extend, don't duplicate).
- `_maybe_recurse` trigger-condition unit tests: fires exactly at
  `confidence.composite < verify_threshold` and `depth < max_step_depth`;
  does not fire above threshold or at max depth.
- Chain-minimum confidence aggregation unit test (2-level and 3-level
  chains, confirm `min()` semantics, not average).
- Max-depth-exhausted degraded-exit unit test (§5).
- `list_child_processes` unit test against `FakeReasoningRepository`.

**Contract:** `ReasoningProcessCompletedPayload`'s new optional field
round-trips through `nova-contracts`' existing payload-registration test
pattern (`test_reasoning_events.py`, extended).

**Integration (fake ports, real FastAPI app):** a scripted Level-4
objective that structurally requires two resolution steps, asserting the
resulting `ReasoningTrace.child_process_ids` has the expected shape (doc
16 §5's structural-verification philosophy — not asserting exact
generated text).

**Real-infrastructure:** none new required — this TDD introduces no new
Postgres table, no new Event Bus subject, no new external dependency.
Existing `reasoning-engine` real-Postgres coverage (if any exists per
task #93's scope) is unaffected.

## 9. Acceptance criteria

1. A scripted Level-4 request whose first-pass decision has
   `confidence.composite` below `verify_threshold` triggers exactly one
   recursion step (structurally asserted, not output-string matched).
2. The recursion never exceeds `max_step_depth` (3, by existing default)
   regardless of how many times the sub-question itself is "unresolved."
3. Aggregate confidence for a multi-step chain equals the minimum across
   the chain, never an average — asserted directly.
4. A Level-1/2/3 request's behavior is provably unchanged (regression
   suite for `REACTIVE`/`ANALYTICAL`/`STRATEGIC`/`GOAL_DRIVEN`/
   `CONSTRAINT_BASED` — the recursion branch must be unreachable from any
   non-`MULTI_STEP` mode).
5. `ReasoningProcessCompletedPayload`'s new field is optional and
   defaulted — an existing consumer parsing the payload without knowledge
   of the new field continues to work unmodified.
